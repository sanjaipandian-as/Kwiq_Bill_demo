# COMPREHENSIVE SECURITY & ARCHITECTURE AUDIT REPORT: ZILLING MOBILE
**Date:** March 17, 2026
**Auditor:** Senior Security Auditor & Software Architect

---

## 1. Overall Rating: 4.5/10
**Status:** High Risk - Improvements Required Before Production Deployment.

The application implements several security layers (AES encryption, SHA256 hashing, Cloud Vault), but the core foundations of these layers are compromised by weak key management and "fail-open" logic. While the architecture is modular, the security implementation relies on predictable data (user email) for encryption keys, which significantly lowers the barrier for data compromise.

---

## 2. Summary of Key Issues
1.  **Predictable Encryption Keys:** The use of `user.email` as the primary AES encryption key makes the encryption virtually useless against an attacker who knows the user's identity.
2.  **Insecure Fallback Logic:** The Google Drive sync service silently defaults to sending plain-text data if the encryption process encounters an error.
3.  **Lack of Brute-Force Protection:** The Manager PIN system (4 digits) can be exhausted in minutes without any lockout mechanism.
4.  **Sensitive Data Exposure in Local Storage:** PIN meta-data and hashes are stored in unencrypted `AsyncStorage`, making them accessible on rooted/compromised devices.
5.  **Sync Integrity Risks:** File-by-file synchronization lacks transactionality, leading to potential data fragmentation between local and cloud storage.

---

## 3. Detailed Bug & Vulnerability List

### [CRITICAL] V01: Fail-Open Encryption Fallback
*   **Location:** `src/services/googleDriveservices.js` (Lines 21-23)
*   **Description:** If `CryptoJS` fails or the key is missing, the `encryptContent` function returns the content in plain text instead of throwing an error.
*   **Impact:** Sensitive business data (invoices, customers, user profiles) could be uploaded to Google Drive in plain text without the user ever knowing.
*   **Fix:** Throw a hard error if encryption fails. Data should NEVER flow unencrypted if secrecy is required.

### [HIGH] V02: Weak Key Derivation (Email-based)
*   **Location:** `src/services/SecurityService.js` and `googleDriveservices.js`
*   **Description:** `user.email` is used directly as the AES key. In security engineering, the email is considered public/knowable information.
*   **Impact:** Anyone with access to the local storage or the Drive folder can decrypt all data using the user's email address.
*   **Fix:** Use PBKDF2 or Scrypt to derive a key from a combination of the email, a random salt, and a device-bound secret (e.g., from `react-native-keychain`).

### [HIGH] V03: No Brute-Force Protection on Manager PIN
*   **Location:** `src/pages/Settings/ManagerPinGate.jsx`
*   **Description:** The verification logic (`handleVerify`) allows unlimited attempts.
*   **Impact:** A 4-digit PIN (10,000 combinations) is trivially easy to crack via script or social engineering (peeking).
*   **Fix:** Implement a 5-attempt limit followed by a 30-second lockout, increasing exponentially.

### [MEDIUM] B01: Base64 Logo Bloat in Settings JSON
*   **Location:** `src/services/googleDriveservices.js` (Line 905)
*   **Description:** The application converts local logo files to Base64 strings and embeds them directly into `settings.json`.
*   **Impact:** This can bloat the JSON file from a few KB to several MB. It increases memory usage during parsing, slows down network sync, and makes the Drive file prone to corruption/timeout.
*   **Fix:** Store the logo as a separate image file in Drive and only store the Drive File ID or a specific relative path in the settings JSON.

### [MEDIUM] B02: Predictable Salt for PIN Hashing
*   **Location:** `src/services/SecurityService.js` (Line 34)
*   **Description:** Using `CryptoJS.SHA256(pin + user.email)` uses a predictable salt.
*   **Impact:** Vulnerable to rainbow table attacks if an attacker gains the hashed PIN from local storage and knows the email.
*   **Fix:** Use a randomly generated salt stored alongside the PIN hash (or better, use the Keychain).

### [LOW] UX01: Missing PIN Recovery Flow
*   **Location:** `src/pages/Settings/ManagerPinGate.jsx`
*   **Description:** There is no "Forgot PIN" button. 
*   **Impact:** If a manager forgets their PIN, they are locked out of critical features (Receptionists/Staff) permanently unless they clear app data.
*   **Fix:** Add a recovery option via Google Re-authentication or an admin-level override.

---

## 4. Suggested Fixes

| Issue ID | Recommended Fix Action | Priority |
| :--- | :--- | :--- |
| **V01** | Replace `return content;` in the catch block of `encryptContent` with `throw new Error('Encryption Failed');`. | Critical |
| **V02** | Implement `react-native-keychain` to store a unique, randomly generated Master Key (AES-256) which is itself protected by biometric/system-level auth. | High |
| **V03** | Add an `attempts` counter to `AsyncStorage`. If `attempts >= 5`, disable the "Authorize" button and show a countdown timer. | High |
| **B01** | Refactor `syncSettingsToDrive` to upload the logo only when it changes, and keep it out of the JSON snapshot. | Medium |
| **B02** | Use `bcrypt` or `argon2` for PIN hashing instead of a single SHA256 pass with a predictable salt. | Medium |

---

## 5. Improvement Recommendations

1.  **Architecture:** Move all security-sensitive logic (hashing, encryption, lockout state) into a dedicated `PrivacyContext` or enhance `SecurityService` to be more autonomous from `SettingsContext`.
2.  **Reliability:** Implement a "Sync Queue" that uses a single atomic operation for Drive updates (e.g., zip all JSONs before upload) to ensure cross-table consistency.
3.  **UX:** Use Native Biometrics (`expo-local-authentication`) as an alternative to the Manager PIN for faster, more secure access.
4.  **Logging:** Implement a secure audit log for PIN verification failures to help users identify if someone is trying to tamper with their settings.
5.  **Code Quality:** Remove redundant `require` calls within service functions. Use standard ES6 imports or move dependencies to the top of the file to prevent circular logic and improve readability.

Vulnerability: Data is sent unencrypted to Google if the CryptoJS library fails. You would never know this happened until your data was leaked.

2. The "Key Under the Doormat" Problem
The app uses user.email as the encryption key for everything on Google Drive.

In security terms, the email address is public info.
If someone gains access to the user's Google Drive (e.g., a shared computer, a lost phone with an open session), they already know the "key" (the email).
They can then run a simple script to decrypt every invoice, customer record, and PIN vault you've synced.
3. The Manager PIN is Vulnerable in the Cloud
The "Security Vault" (security_vault.json) that stores the Manager PIN on Google Drive is also encrypted with the same user.email key.

If that file is intercepted or accessed by an unauthorized person, they can decrypt the vault, see the PIN, and gain full control over the "Receptionist" and "Staff" management sections of your app.
4. Lack of Data Integrity
There is no "Signature" (HMAC) on the files in the cloud. An attacker who gains access to the Drive could modify your invoice JSON files (e.g., change price amounts or customer details) and re-encrypt them using the email key. When your app "Restores," it would accept this tampered data as legitimate.

Summary: Local vs. Cloud
Local Storage: High risk because it's effectively unencrypted (hashes are predictable).
Google Sync: High risk because the "encryption" is using a public value (email) as a password and has a "fallback to plain-text" bug.
The Fix is the same for both: We must move away from using user.email as a key. We should generate a Unique Hardware-Bound Master Key on the phone's secure hardware (Keychain/Keystore) that never leaves the device. That way, even if someone steals the files from Google Drive, they can't decrypt them without the physical phone.
